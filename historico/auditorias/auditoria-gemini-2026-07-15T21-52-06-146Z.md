Análise técnica do projeto **tripvisuals** realizada sob a perspectiva de um auditor técnico sênior.

---

## Segurança

### 1. Autenticação e Armazenamento de Credenciais
*   **Senha em texto plano (Plaintext):** O arquivo `server.js` valida o acesso comparando a senha enviada diretamente com a variável de ambiente `process.env.ADMIN_PASSWORD` (`timingSafeStringCompare(senha, process.env.ADMIN_PASSWORD)`). Não há uso de algoritmos de hash seguros (como bcrypt, argon2 ou PBKDF2). Se o ambiente for comprometido, a credencial administrativa é exposta imediatamente.
*   **Vazamento de tamanho no Timing Attack:** A função `timingSafeStringCompare` tenta mitigar ataques de tempo, mas falha ao tratar comprimentos diferentes:
    ```javascript
    if (ba.length !== bb.length) {
        crypto.timingSafeEqual(bb, bb);
        return false;
    }
    ```
    Como o tempo de execução de `crypto.timingSafeEqual` é proporcional ao tamanho do buffer comparado, um atacante consegue deduzir o comprimento exato da senha administrativa testando entradas de tamanhos diferentes e medindo as variações de milissegundos na resposta.

### 2. Content Security Policy (CSP) vs. Realidade do Código
*   O servidor define uma política estrita em `server.js` sem a diretiva `'unsafe-inline'` para estilos:
    `style-src 'self' https://fonts.googleapis.com;`
*   No entanto, os arquivos `admin-landing.html` (linhas 251, 253, 255) e `admin-sobre.html` (linhas 128, 130) contêm atributos de estilo inline (`style="..."`). Sob a CSP configurada, o navegador **bloqueará** a renderização desses estilos, quebrando elementos visuais do painel administrativo.

### 3. Validação de Entrada (CPF/CNPJ)
*   No backend (`server.js`), a rota `/api/checkout/pix` apenas valida se o comprimento do CPF/CNPJ é de 11 ou 14 caracteres numéricos:
    ```javascript
    const cpfDigits = String(cpfCnpj || '').replace(/\D/g, '');
    if (cpfDigits.length !== 11 && cpfDigits.length !== 14)
        return res.status(400).json({ error: 'CPF/CNPJ inválido.' });
    ```
    Não há validação de integridade (dígitos verificadores) no servidor. CPFs matematicamente inválidos (ex: `000.000.000-00`) serão enviados à API do Asaas, gerando falhas de integração em tempo de execução ou poluindo o cadastro do gateway de pagamento.

### 4. Injeção de Fórmulas (CSV Injection)
*   A rota `/api/pedidos/export` gera um arquivo CSV concatenando strings diretamente. Valores inseridos por usuários (como nome do cliente ou observações do pedido) não são sanitizados contra caracteres de controle de fórmulas (`=`, `+`, `-`, `@`). Se um administrador abrir o relatório exportado no Excel ou LibreOffice, códigos maliciosos inseridos nos campos de texto poderão ser executados localmente.

## Arquitetura e consistência

### 1. Acoplamento no `server.js`
*   O arquivo `server.js` atua como um "monólito de arquivo único". Ele acumula responsabilidades de:
    *   Inicialização e migração de tabelas do banco de dados.
    *   Gerenciamento e expiração de sessões customizadas.
    *   Definição de rotas, middlewares de segurança e limites de requisição (Rate Limiting).
    *   Lógica de negócios (Controllers) e comunicação direta com serviços externos (Cloudinary, Asaas).
*   Isso dificulta a manutenção e viola o princípio de responsabilidade única.

### 2. Duplicação de Código no Frontend
*   **Toasts de Notificação:** A função de renderização de toasts (`mostrarToast` / `showToast`) é copiada e colada com pequenas variações em `admin-hub.js`, `admin-layout.js`, `admin-pedidos.js`, `admin-produtos.js`, `admin-landing.js` e `admin-sobre.js`.
*   **Sanitização de HTML (XSS):** O helper de escape de caracteres (`escapeHTML` / `esc`) é redefinido individualmente em `admin-landing.js`, `admin-pedidos.js`, `admin-produtos.js`, `admin-upload.js` e `catalogo.js`.
*   Esses utilitários deveriam estar centralizados em um único arquivo compartilhado (como o `admin-shared.js`).

## Cobertura de testes

*   **Realidade:** **0% de cobertura.** Não existem frameworks de teste (Jest, Mocha, Cypress) declarados no `package.json`, nem arquivos de teste (`.test.js` ou `.spec.js`) no repositório.
*   **Casos de borda críticos não testados:**
    *   Comportamento do sistema quando a API do Asaas ou Cloudinary falha ou retorna timeout.
    *   Condições de corrida (Race Conditions) na criação concorrente de clientes no Asaas via `/api/checkout/pix`.
    *   Persistência e expiração de sessões no banco de dados sob fusos horários conflitantes entre o servidor Node e o PostgreSQL.

## Tratamento de erros

*   **Ponto positivo:** O tratamento global de erros no Express e nas rotas individuais é bem-comportado. Erros internos do banco de dados ou do sistema de arquivos não são expostos diretamente ao cliente final, sendo substituídos por mensagens genéricas como `"Erro interno do servidor."` ou `"Erro ao buscar produtos."`, enquanto o erro real é enviado ao `console.error` e opcionalmente ao Sentry.
*   **Falha silenciosa no Webhook:** No endpoint `/api/webhook/asaas`, se ocorrer um erro ao processar o pagamento, o servidor captura a exceção, grava no banco de dados e responde com status `200 OK`:
    ```javascript
    } catch (e) {
        console.error('Webhook Asaas processing error:', e.message);
        if (logId) await pool.query('UPDATE webhook_log SET erro = $1 WHERE id = $2', ...);
        res.status(200).json({ received: true, processed: false });
    }
    ```
    Embora isso evite que o Asaas bloqueie a fila de envio por tentativas falhas, o erro é tratado de forma totalmente silenciosa para o gateway, exigindo monitoramento manual constante da tabela `webhook_log`.

## Documentação vs. realidade

*   **Alegação (README.md):** *"Login com hash de senha + comparação timing-safe (resistente a timing attacks)"*
    *   **Realidade:** **Falso.** A senha é comparada em texto plano (plaintext) e a função de comparação de tempo vaza o comprimento da senha devido ao desvio de fluxo condicional baseado no tamanho do buffer.
*   **Alegação (README.md):** *"Vulnerabilidades: 0 (auditoria mais recente: 27/27 controles)"*
    *   **Realidade:** **Inconsistente.** A presença de estilos inline em páginas administrativas sob uma CSP estrita impede o funcionamento correto do painel nos navegadores modernos.
*   **Alegação (PATCH_NOTES.md):** *"Toda a infraestrutura já está no código e já foi testada na medida do possível"*
    *   **Realidade:** Não há testes automatizados de nenhuma natureza no projeto.

## Achados por severidade

### CRÍTICO

#### 1. Senha do Administrador em Texto Plano e Vazamento de Comprimento (Timing Attack)
*   **Arquivo:** `server.js` | Linhas ~30-41 e ~360-375
*   **Trecho:**
    ```javascript
    function timingSafeStringCompare(a, b) {
        const ba = Buffer.from(String(a || ''));
        const bb = Buffer.from(String(b || ''));
        if (ba.length !== bb.length) {
            crypto.timingSafeEqual(bb, bb);
            return false;
        }
        return crypto.timingSafeEqual(ba, bb);
    }
    ```
*   **Impacto:** A senha administrativa é armazenada sem hash. Adicionalmente, a lógica de comparação permite que atacantes descubram o comprimento exato da senha medindo o tempo de resposta do servidor.

#### 2. Violação de CSP por Estilos Inline no Painel Administrativo
*   **Arquivos:** `admin-landing.html` (Linhas ~251, ~253, ~255), `admin-sobre.html` (Linhas ~128, ~130) e `server.js` (Linhas ~180-200)
*   **Impacto:** O navegador bloqueará a execução dos estilos inline devido à política estrita de CSP aplicada pelo servidor, quebrando o layout e a usabilidade do painel de administração.

### IMPORTANTE

#### 1. Ausência de Validação de Integridade de CPF/CNPJ no Servidor
*   **Arquivo:** `server.js` | Linhas ~630-645
*   **Trecho:**
    ```javascript
    const cpfDigits = String(cpfCnpj || '').replace(/\D/g, '');
    if (cpfDigits.length !== 11 && cpfDigits.length !== 14)
        return res.status(400).json({ error: 'CPF/CNPJ inválido.' });
    ```
*   **Impacto:** Permite o envio de documentos inválidos para a API externa do Asaas, gerando falhas de integração em produção e poluição de dados.

#### 2. Vulnerabilidade de CSV Injection na Exportação de Pedidos
*   **Arquivo:** `server.js` | Linhas ~550-570
*   **Trecho:**
    ```javascript
    const csv = header + rows.map(p => [ ... ].join(',')).join('\n');
    ```
*   **Impacto:** Dados inseridos por clientes (como nomes ou notas) contendo caracteres como `=`, `+`, `-` ou `@` podem executar comandos ou macros maliciosas quando o arquivo CSV for aberto em softwares de planilha (Excel, Google Sheets).

#### 3. Inexistência de Testes Automatizados
*   **Arquivo:** `package.json` | Todo o repositório
*   **Impacto:** Qualquer alteração futura no código (especialmente na integração de pagamentos) pode introduzir regressões críticas sem detecção prévia.

---

### SUGESTÃO

#### 1. Duplicação Excessiva de Funções Utilitárias no Frontend
*   **Arquivos:** `admin-hub.js`, `admin-layout.js`, `admin-pedidos.js`, `admin-produtos.js`, `admin-landing.js`, `admin-sobre.js` e `catalogo.js`
*   **Impacto:** Dificulta a manutenção do código. Correções de bugs em funções de escape ou exibição de mensagens precisam ser replicadas manualmente em múltiplos arquivos.

#### 2. Comparação de Token de Webhook não é Timing-Safe
*   **Arquivo:** `server.js` | Linhas ~690-705
*   **Trecho:**
    ```javascript
    if (!expectedToken || !incomingToken || incomingToken !== expectedToken)
    ```
*   **Impacto:** Embora difícil de explorar na prática para webhooks, a comparação direta de strings é suscetível a timing attacks. Recomenda-se o uso de `crypto.timingSafeEqual`.
