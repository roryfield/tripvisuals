Método VDZN-SM

Este documento não fala sobre o Tripvisuals. Fala sobre como o trabalho no Tripvisuals foi feito — os princípios por trás de cada acerto e cada erro, generalizados pra funcionar em qualquer projeto que o VDZN-SM tocar depois. Os 3-4 projetos que estão esperando o método amadurecer são o teste real: se esses princípios só fizeram sentido pro Tripvisuals, o método não generalizou. Se fizerem sentido em qualquer stack, generalizou.

1. Confirmar com dado real, nunca com aparência

O padrão que se repetiu mais vezes nesta sessão inteira. Toda vez que alguma coisa "parecia" estar funcionando — visualmente, na tela — e a suposição foi trocada por uma checagem de dado real, o resultado foi diferente do esperado. Quatro exemplos concretos, cada um generalizável:

  • Um gráfico "existia" (instância JavaScript criada, dado correto) mas não tinha um único pixel desenhado na tela. Só apareceu ao contar pixel real do canvas, não ao olhar a captura.
  • Um "deploy aplicado" foi confirmado errado até cruzar a mensagem exata do commit no Git com o que o código realmente continha.
  • Um botão "quebrado" tinha causa raiz num CSS com quatro cópias de uma regra que se contradiziam — só apareceu ao ler o CSS de verdade, não ao adivinhar pela sintoma visual.
  • Uma correção "funcionando" só foi confirmada depois de 5 recarregamentos seguidos com checagem de pixel, porque o bug original era intermitente — uma confirmação só não bastava.

Regra prática pro método: sempre que uma alegação de "está funcionando" puder ser verificada por um número, um valor computado, ou um log — verifica. "Parece" não é evidência.

2. Verificação sistemática antes de qualquer remoção estrutural

Ao fundir três telas numa só (a Oficina), um elemento funcional foi removido sem querer, escondido dentro de um bloco de cabeçalho que parecia só decorativo. A correção não foi só "devolver o elemento" — foi construir um script que cruza todo id referenciado pelo JavaScript contra todo id presente no HTML, sistematicamente, antes de qualquer remoção estrutural futura.

Regra prática pro método: antes de remover qualquer bloco de HTML/estrutura numa refatoração, roda essa checagem cruzada. Não confia em leitura visual do código pra saber o que está "só decorativo" — confia em busca sistemática.

3. Relaxar proteção sempre no escopo mais estreito possível

Duas decisões de segurança nesta sessão seguiram o mesmo princípio: quando uma política de segurança (CSP) precisou ser relaxada pra permitir uma funcionalidade nova, a exceção foi escrita pra uma rota específica, não pro site inteiro — e quando uma biblioteca de terceiro (Chart.js) foi bloqueada por essa mesma política, a solução não foi abrir uma exceção nova, foi hospedar a biblioteca localmente, mantendo a política original intacta.

Regra prática pro método: toda vez que uma proteção existente parecer "atrapalhar" uma funcionalidade nova, a primeira pergunta é "dá pra manter a proteção e resolver de outro jeito?", não "como eu abro uma exceção".

4. Separar decisão de design de decisão técnica

Antes de programar o painel de comando do Catalogador, três esboços visuais foram construídos e comparados — só depois de uma escolha explícita é que o código começou. Isso evitou programar duas vezes a mesma coisa por causa de gosto não alinhado antes da implementação.

Regra prática pro método: qualquer decisão de interface com peso visual real (não um ajuste pequeno) merece uma etapa de esboço/comparação antes do código, mesmo que pareça "perder tempo" no primeiro momento. É mais barato que reescrever depois.

5. Pacote fechado, manifesto único — nunca entrega fragmentada

O padrão de "aplicar só uma parte do pacote" se repetiu pelo menos três vezes nesta conversa, sempre causando o mesmo tipo de confusão (funcionalidade pela metade, sem saber o que realmente estava no ar). A solução que funcionou não foi "ser mais cuidadoso" — foi mudar o processo: nunca entregar arquivo solto quando existe um pacote maior em andamento, sempre fechar com uma lista explícita e completa antes de considerar pronto.

Regra prática pro método: toda entrega de mais de um arquivo termina com uma lista explícita e numerada de tudo que precisa ser aplicado junto, nunca assumindo que "os arquivos anteriores já foram aplicados".

6. Protocolo de verificação em duas camadas: automatizada + visual

Documentos que já funcionam bem no Tripvisuals e valem virar padrão do método:

  • Protocolo Refresh (PROTOCOLO-REFRESH.md): testar fora do navegador (terminal, dado bruto) antes de propor um segundo patch de código. Evita gastar uma tentativa de correção em cima de um diagnóstico ainda não confirmado.
  • Checklist de aplicação + verificação ao vivo: depois de qualquer pacote de mudança, existe uma lista concreta do que testar, na ordem que revela problema de interação entre partes, não só cada peça isolada.

O que NÃO generalizar

Importante registrar isso também — nem tudo que funcionou aqui é método, parte é só contexto específico do Tripvisuals:

  • O uso de Cloudinary, Groq, Railway são escolhas de fornecedor deste projeto, não parte do método.
  • A estética VDZN Signature (cyan/roxo neon) é identidade visual da marca do cliente, não um padrão de design a impor em outro projeto.
  • O fato de o admin ter login único, sem papéis de usuário, foi uma decisão de escopo deste projeto específico — outro projeto pode genuinamente precisar de multi-usuário desde o início.

Como usar este documento

Não é pra ler uma vez e arquivar. É pra abrir no início de cada novo projeto do VDZN-SM e perguntar, item por item: "esse princípio já está sendo seguido aqui, ou preciso lembrar de aplicá-lo?". Se um princípio genuinamente não se aplicar a um projeto (ex: um projeto sem interface visual não precisa do item 4), tudo bem — o teste é se ele generalizou em conceito, não se toda linha se aplica literalmente em todo lugar.

Protocolo Refresh

Este documento existe porque um incidente real (Catalogador travado, SSE quebrado em produção) tomou tempo demais pra resolver, com ciclos de teste que podiam ter sido cortados pela metade. Não é teoria. Cada etapa abaixo nasceu de um ponto específico onde a investigação real perdeu tempo, e existe pra cortar esse tempo da próxima vez.

Sete camadas de pensamento, cada uma resolvendo um tipo diferente de perda de tempo. No fim, viram uma seção própria do vdzn-sm — o "botão Refresh" — descrito por último.

1. Criativo — "Existe caminho mais simples pro mesmo resultado?"

Antes de implementar o pedido literalmente, pergunta: essa é a forma mais simples de resolver isso, ou é só a primeira que veio à cabeça?

Regra prática: entre duas formas de entregar a mesma funcionalidade, prefira sempre a que já tem uso comprovado no projeto sobre a que introduz um mecanismo novo — mesmo que a nova pareça "mais correta" ou "mais moderna" no papel.

Aplicado ao incidente real: o Catalogador usava SSE (conexão aberta e contínua) pra mostrar progresso em tempo real. Toda outra tela do admin já resolve isso com polling ou atualização sob demanda — nenhuma outra tela do projeto depende de conexão longa. SSE era a peça nova, nunca testada contra o Railway em produção, resolvendo um problema (ver progresso ao vivo) que polling já resolve com 90% da qualidade e uma fração do risco. Isso devia ter sido sinalizado no momento em que o SSE foi construído, não descoberto quebrado meses depois.

Pergunta de bolso pra qualquer feature nova: "se essa peça específica falhar em produção, sobra alguma coisa funcionando, ou trava tudo?" Se a resposta for "trava tudo", já é sinal de escolher algo mais robusto.

2. Operacional — "Onde pode estar o problema, e qual é o teste mais barato pra cada lugar?"

Antes de mexer em qualquer código, mapeia as camadas possíveis, na ordem do teste mais barato pro mais caro:

  1. Código do navegador (JS quebrado, elemento errado) — testável em segundos, DevTools Console.
  2. Código do servidor (lógica errada, rota errada) — testável lendo o código-fonte real.
  3. Infraestrutura entre os dois (proxy, CDN, plano de hospedagem) — só testável com uma chamada que não passa pelo navegador, tipo curl puro.

A regra que faltou no incidente real: "clique não faz nada, sem nenhum erro em lugar nenhum" é uma assinatura específica. Não é bug de lógica (bug de lógica geralmente produz algum erro, em algum lugar). Silêncio total, em todas as camadas visíveis, aponta pra camada 3 — infraestrutura — quase sempre. Essa camada devia ter sido testada com curl direto na primeira rodada de investigação, não na quinta. Cada rodada de "aplica isso e testa nas telas" custou um ciclo de deploy inteiro; um curl custa 20 segundos.

Checklist antes de sugerir "aplica esse patch e testa": - [ ] Esse patch resolve uma causa confirmada, ou é uma hipótese? - [ ] Se for hipótese, existe um teste mais barato que confirma ou descarta ela antes de pedir um novo deploy? - [ ] Depois de 2 tentativas sem sucesso no mesmo sintoma, a pergunta muda de "qual é o bug" pra "essa abordagem inteira é a errada" — trocar de estratégia é uma opção válida, não é desistir.

3. Lógico — "Isso já é um problema conhecido, documentado por outra pessoa?"

Antes de tratar um sintoma como mistério exclusivo deste projeto, busca se é um padrão já documentado pra essa combinação específica de tecnologia + hospedagem.

Aplicado ao incidente real: SSE + HTTP/2 + proxy de plataforma (Railway, Vercel, Render, etc.) é uma combinação com problemas conhecidos e documentados publicamente — não é exclusividade do Tripvisuals. Isso devia ter sido pesquisado explicitamente ("Railway server-sent events not working", "SSE HTTP/2 proxy buffering") antes da segunda tentativa de patch, não só resolvido por dedução a partir da especificação do HTTP/2.

Regra prática: qualquer sintoma envolvendo conexão longa, streaming, WebSocket, ou comportamento que muda entre local e produção, merece uma busca explícita por "[tecnologia] + [nome da plataforma de hospedagem] + known issues" antes de qualquer segunda tentativa de correção. Primeira tentativa pode ser dedução; segunda tentativa em diante, sem confirmar contra o que já é sabido publicamente, é perda de tempo evitável.

4. Crítico — pós-morte de toda decisão de risco

Depois que uma correção é aplicada e confirmada funcionando, reavaliar depois de um tempo, com essas três perguntas:

  1. Quantos ciclos de teste foram necessários até a causa real ser confirmada?
  2. Em que ciclo específico a causa real já estava disponível, mas não foi reconhecida?
  3. O que precisa mudar no processo (não no código) pra esse mesmo tipo de sintoma ser resolvido mais rápido da próxima vez?

Pós-morte do incidente real, aplicado agora: 1. Cinco ciclos de teste (print → patch → print → patch → curl decisivo) até a causa raiz completa ficar clara. 2. A resposta certa já estava disponível no ciclo 3 — a saída vazia de curl -N provava definitivamente que era infraestrutura, não código. Achado só no ciclo 5 porque o teste com curl só foi sugerido depois de duas tentativas de patch no código. 3. Mudança de processo: qualquer sintoma "nada acontece, sem erro nenhum, em produção" pula direto pra teste com curl/linha de comando, antes de qualquer segunda hipótese de código. Isso vira regra fixa, não sugestão pontual — ver seção 7.

5. Analítico / documentacional — registrar pra não redescobrir

Todo diagnóstico não-trivial (mais de uma tentativa até acertar) devia virar uma entrada permanente, não só histórico de conversa. Documento vivo, curto, por sintoma:

Sintoma Causa real Como confirmar rápido Correção aplicada
Clique não faz nada, sem erro no console, request confirmado 200 no servidor Conexão de streaming (SSE) descartada por infraestrutura entre Railway e navegador curl -N direto, sem navegador, contando bytes recebidos em 15s Trocado SSE por polling a cada 1.5s nas mesmas rotas já comprovadas (/status, /results)

Esse formato de tabela é o que deve crescer no projeto, arquivo próprio (proponho PROBLEMAS-CONHECIDOS.md, no mesmo nível de CONTINGENCIA.md). Da próxima vez que "clique não faz nada" aparecer, a primeira ação é consultar essa tabela antes de reabrir investigação do zero.

6. Oportunidades / riscos — antecipar antes de precisar apagar incêndio

Pra toda peça nova que depende de comportamento de infraestrutura não testável localmente (conexão longa, webhook, fila assíncrona, qualquer coisa que só se comporta "de verdade" depois do deploy), perguntar no momento de construir, não depois de quebrar:

  • Isso tem como ser testado localmente de verdade, ou só vai ser validado ao vivo, em produção, na frente do cliente?
  • Se isso falhar silenciosamente (sem erro, sem exceção), como alguém vai descobrir que falhou?
  • Existe uma versão mais simples e menos arriscada que entrega 80% do valor com 20% do risco?

Isso não é burocracia — é a pergunta que, se feita quando o SSE foi construído, teria trocado ele por polling antes de qualquer cliente ver a tela travada.

7. Consultoria / auditoria — o módulo "Refresh"

Esta é a seção que vira funcionalidade de verdade dentro do vdzn-sm, não só texto de referência.

O que é: um botão/comando único que roda as seções 2, 3 e 5 acima automaticamente contra qualquer sintoma reportado, antes de qualquer patch novo ser proposto. Na prática, um checklist disparável, não um botão literal (ainda) — mas desenhado pra virar um se fizer sentido num painel de administração futuro do vdzn-sm.

Sequência fixa que o Refresh roda, nessa ordem, sem pular etapa:

  1. Mapa de camadas (seção 2) — onde pode estar, do teste mais barato pro mais caro.
  2. Busca por padrão conhecido (seção 3) — isso já foi documentado por alguém fora deste projeto?
  3. Consulta a PROBLEMAS-CONHECIDOS.md (seção 5) — isso já aconteceu aqui antes?
  4. Só depois dessas três, uma hipótese de correção é proposta — e vem etiquetada como confirmada (testada e comprovada) ou hipótese (ainda não comprovada), nunca misturado, pra quem está lendo saber o nível de certeza antes de gastar um ciclo de deploy nela.
  5. Depois de aplicada e confirmada: uma entrada nova em PROBLEMAS-CONHECIDOS.md, sem exceção — é isso que faz o próximo Refresh ser mais rápido que este.

Nome de trabalho: Protocolo Refresh. Fica valendo pra qualquer investigação de bug daqui pra frente neste projeto, não só pra este incidente.

Estrutura do Guia Contextual

Este documento é a "lógica e estrutura" que você pediu — o motor (admin-guia.js) já existe e já está provado funcionando no Catalogador IA. O resto do sistema segue exatamente o mesmo padrão, é questão de escrever a lista de passos de cada fluxo, não reinventar o mecanismo.

O padrão, resumido

Inspirado no MTG Arena, mas mais simples de propósito: nunca bloqueia a tela inteira. Se o usuário ficar parado depois de começar um processo, aparece um destaque sutil (contorno pulsante) no elemento certo, com um balão de dica ao lado explicando o que fazer. Quando a ação certa acontece, uma confirmação rápida (✓ verde) aparece e o guia avança sozinho pro próximo passo. Se o usuário já sabe o que fazer e age antes da dica aparecer, ela nunca chega a aparecer — não atrapalha quem já é fluente no sistema.

Por que não bloquear outras ações (diferente do MTGA "puro")

O MTG Arena pode travar ações irrelevantes porque é um jogo com regras fixas — só existe um próximo movimento válido por vez. Um painel administrativo não é assim: a dona da loja pode legitimamente querer fazer outra coisa no meio de um processo (checar um pedido, por exemplo) sem isso ser "errado". Por isso o guia aponta, não impede — decisão de design, não limitação técnica.

Como cada novo fluxo se registra (3 passos, sempre os mesmos)

  1. Lista de passos, cada um com: qual elemento apontar (seletor CSS), qual mensagem mostrar, e como saber que aquele passo foi cumprido (condicaoAvanco, uma função que olha o estado já visível na tela — nunca precisa inventar chamada de rede nova, os contadores já existem).
  2. Gatilho de início — geralmente o evento de troca de aba que já existe (vz-oficina-tab na Oficina; Marca & Vitrine e Pedidos precisariam de um evento equivalente, mesmo padrão).
  3. Um arquivo .js pequeno, só com essa lista — nunca precisa tocar no motor (admin-guia.js) nem na lógica de negócio da tela em si.

Mapa de onde aplicar em seguida — pendência estruturada, não vaga

Marca & Vitrine

  • Passo 1: aponta pros 5 cards de estilo. Avança quando um estilo é selecionado (evento de clique já existe).
  • Passo 2: aponta pro botão "Prévia ao vivo do catálogo". Avança quando o painel abre.
  • Passo 3: aponta pra "VER AO VIVO". Sem condição de avanço (é o fim do fluxo, só uma sugestão final).

Pedidos

  • Passo 1: aponta pro botão "+ Novo Pedido" (ou "Novo via comprovante", dependendo de qual a loja usa mais). Avança quando um pedido é criado.
  • Passo 2, condicional: se o pedido criado tiver status: novo, aponta pro card do pedido, sugerindo mudar pra "Confirmado" quando o pagamento cair.
  • Passo 3: aponta pra "Configurar frete por região" só na primeira visita (não repetir depois que já configurou pelo menos uma região — isso vira uma condição extra de nem sequer iniciar o fluxo, não só de avançar).

Hub

Só faz sentido um passo único: na primeira visita de todas (conta nova), aponta pra sidebar, mensagem tipo "Essa barra lateral leva pra tudo — Oficina cadastra produto, Marca & Vitrine cuida da loja, Pedidos organiza venda." Não é um fluxo de várias etapas, é uma apresentação de uma vez só.

Extensão natural — "primeira vez" vs "sempre"

Faz sentido guardar (localStorage, por navegador, sem precisar de tabela nova no banco) quais fluxos o usuário já completou uma vez, e não repetir o guia automático depois disso — só reaparece se a pessoa pedir explicitamente ("relembrar como funciona", um botão pequeno, mesma ideia do "Replay Tutorial" que aparece no seu vídeo de referência do MTGA). Isso não está implementado ainda no motor atual (que sempre reativa a cada visita à aba) — é o próximo incremento natural, registrado como pendência abaixo.

A parte que você disse pra não construir agora — só deixando a lógica escrita

A "tela de tutoriais com todos os tópicos", linkando pra um site futuro (fórum, base de conhecimento, suporte, comercial) — a peça que falta pra isso se conectar ao que já existe é só um índice central: uma tela (poderia viver dentro do próprio Manual que já existe) listando todos os fluxos que têm guia contextual, com um botão "relembrar esse fluxo" em cada um — que simplesmente chama VZGuia.iniciarFluxo(nome, passos) de novo, manualmente. O link pro site externo é só isso mesmo, um link — não precisa de nada especial de lógica, só existir quando o site existir.

Tripvisuals — projeto

Limitações Técnicas

Diferente de AJUSTES-PENDENTES.md: isso não é lista de bug ou trabalho faltando. É fronteira real de arquitetura — coisas que o sistema deliberadamente não faz hoje, o motivo técnico ou de negócio por trás, e o que precisaria mudar pra resolver. Útil pra conversa com cliente ("por que não X") e pra decisão de prioridade.

Acesso e permissão

Login único, compartilhado. Não existe conceito de "usuário" — quem tem a senha (ou o hash dela) vê e faz tudo. Não dá pra dar acesso limitado pra um funcionário, nem saber quem fez o quê além do que já fica registrado em system_events (que loga a ação, não quem a fez, porque não existe "quem" separado de "a conta").

Por quê: decisão consciente de escopo, não limitação técnica de fundo. Construir usuários/papéis de verdade é a "Fase 13", registrada como pendência de design desde o VERSIONING.md original — precisa de decisão sua sobre quantos níveis de acesso fazem sentido antes de eu construir.

Pagamento e frete

PIX automático existe no código, mas está desligado. A integração com Asaas (gerar cobrança, confirmar pagamento automaticamente) está pronta, testada em sandbox, mas trancada atrás de duas condições que precisam estar certas ao mesmo tempo: ASAAS_API_KEY configurada e a flag checkout_automatico_enabled ligada. As duas dependem do CNPJ da loja ser aprovado — sem isso, tecnicamente não tem como ativar de verdade.

Frete é estimativa manual por estado, não frete real de transportadora. Você cadastra um valor fixo por UF; o sistema calcula automaticamente a partir do CEP do cliente, mas não é o valor real dos Correios/transportadora — é o que você decidiu cobrar. Automação de frete real (cotação via API de transportadora) também depende do CNPJ.

Por quê: sem CNPJ, não existe conta empresarial pra contratar API de pagamento nem de transportadora — a chave pessoal recebe PIX manual, e frete combinado é a alternativa que não depende disso.

Catalogador IA e comprovante

A IA não cria pedido completo a partir de um comprovante sozinha, e não pode. Um comprovante de PIX carrega valor, data e nome de quem pagou — nada sobre o que foi comprado, tamanho, cor ou endereço. Isso não é limitação de engenharia, é limitação do próprio dado: essa informação não existe na imagem. O sistema cria um rascunho com o que dá pra extrair e para aí, esperando confirmação humana.

Modelo da Groq pode ficar desatualizado sem aviso. Já aconteceu uma vez nesta mesma sessão — um modelo que funcionava parou de existir no catálogo da Groq, sem aviso prévio. O nome do modelo vive numa variável de ambiente (CATALOGADOR_MODEL) exatamente por causa disso, mas ainda exige alguém notar o problema e trocar manualmente quando acontecer de novo.

Plano gratuito da Groq tem teto real de token por minuto, não só de requisição — o sistema já usa um limitador conservador (10 req/min por padrão) pensado pra isso, mas em volume muito alto (milhares de imagens de uma vez), ainda esbarra no limite do plano. Resolve com upgrade de plano na Groq, não com mudança de código.

Infraestrutura

Um servidor, uma região (Railway, us-west2), plano Hobby. Sem failover automático — se o Railway tiver uma interrupção regional, o site fica fora do ar até eles resolverem, não tem servidor backup assumindo sozinho. Pro volume atual de uma loja, isso é proporcional ao risco real; não é dimensionado pra tráfego de grande escala sem revisão.

Suíte de testes automatizados existe no código, mas nunca rodou de verdade. 45 verificações escritas, prontas, nunca executadas contra um Postgres real — porque isso exige decidir onde rodar esse banco de teste (Docker é o caminho mais simples), e essa decisão ainda está em aberto.

server.js é um arquivo único, grande. Funciona, mas é dívida de manutenção — mexer em qualquer rota exige entender o arquivo inteiro, não um módulo isolado. Não é vulnerabilidade, é o tipo de coisa que fica mais custosa de manter conforme o sistema cresce.

Navegação e interface (pós v2.0)

Botão de trocar tema (claro/escuro) só existe na tela do Hub. Nas outras telas, pra trocar de tema é preciso voltar pro Hub primeiro. Não é bug, é ausência — o botão nunca foi replicado nas outras telas quando foi construído.
